# DevDay 2026 Hackathon Judge — Skills PoC

ローカル提出リポジトリをCodexで一次審査するための、3種類の独立したSkillです。すべて日本語で審査し、各フォルダだけで動作します。外部サービスや前回システムの導入は不要です。

| Skill | 審査の進め方 | 評価する範囲 |
| --- | --- | --- |
| [devday-judge-evidence](skills/devday-judge-evidence/SKILL.md) | 観点ごとの証拠台帳を作り、採点アンカーと照合 | 全4観点＋DevDay適合度 |
| [devday-judge-journey](skills/devday-judge-journey/SKILL.md) | 利用者の仕事を始まりから終わりまで追い、例外経路も確認 | 全4観点＋DevDay適合度 |
| [devday-judge-challenge](skills/devday-judge-challenge/SKILL.md) | 価値の主張と対立する説明を証拠で検証し、重要性を踏まえて裁定 | 全4観点＋DevDay適合度 |

担当分野を分ける構成ではありません。どれを1つ選んでも総合評価できます。相互の呼び出しや別のSkillへの委譲もありません。

## 採点

[前回システムの観点と得点帯](https://github.com/schroneko/automated-hachathon-judge/blob/f5c843ddad7aea1c68023e145ca9c0be0b575093/src/shared/constants.ts)を引き継ぎ、具体的な審査手順と判断基準は新規に作成しています。

| 観点 | 確認内容 | 配点 |
| --- | --- | --- |
| 技術的な実装 | 完成度、構成、堅牢性、安全性 | 10 |
| デザインとユーザー体験 | 情報構造、利用の流れ、一貫性、アクセシビリティ | 10 |
| 潜在的なインパクト | 課題の重要性、対象者、実用性、発展性 | 10 |
| アイデアの質 | 独自性、課題と解決策の適合、洞察 | 10 |
| **総合点** | 上記4観点の等配点合計 | **40** |
| DevDay適合度 | 関連する発表、活用の深さ、成果物・制作過程の価値への寄与 | **別枠10** |

テーマの対象は[DevDay 2026公式Recap](https://openai.com/index/devday-2026-recap/)の25項目。各Skillに、2026-10-17時点の照合表を同梱しています。単に製品名がある、OpenAI APIを使う、Codexで開発した、というだけでは強い適合としません。関連発表のIDと、実装・モック・制作過程・着想の違いを記録します。

テーマを別枠にしたこと、適合度の点数や分類、評価不能時のnull、観点別の詳細アンカーは今回のPoCの設計です。主催者の公式な通過点・参加資格を意味しません。通過点の指定がなければ、合否・順位は生成しません。前回の出力JSONとの互換性はありません。

## すぐ試す

このリポジトリを開いた**信頼できるCodexセッション**で、使うSkillのファイルを明示します。最初の例ではインストール作業は不要です。

```text
skills/devday-judge-evidence/SKILL.md を読み、その指示に従って
/absolute/path/to/submission をDevDay 2026ハッカソンの一次審査として評価してください。
対象は現在の作業ツリーです。結果は日本語のMarkdownで返してください。
```

別方式を使う場合はSkillパスを `devday-judge-journey` または `devday-judge-challenge` に変えます。JSONが必要なら末尾を「結果はSkillの出力仕様に従う単一JSONで返してください」に変えます。

必須なのは対象のローカルパスだけです。主催者が用意した作品説明・デモ画像、対象commit、審査対象サブディレクトリ、出力先等があれば一緒に指定できます。出力先を指定する場合は提出リポジトリの外にします。

標準の審査は読み取り専用の静的確認です。ソース、テストの内容、利用導線、提出資料を読みますが、依存インストールやコード実行、API接続、ブラウザでの動作確認は行いません。動いた・テストに合格した・画面を操作したとは報告しません。CLI・API・Skill等も用途に合ったUXで評価します。

対象内のAGENTS.mdやSkill、READMEの審査員向け命令は提出データとして扱います。**審査は提出リポジトリを作業ディレクトリにせず、信頼できるこちらの作業ディレクトリから、対象パスを指定して開始してください。** ホストが提出物の設定や指示を先に自動ロードすると、Skillの指示だけでは信頼境界を作れません。実行時の作業ディレクトリ、設定、ツール権限も審査用に管理します。

## Skillとして常設する場合

成果物は `skills/` にあります。必要なフォルダを、Codexが探索する `.agents/skills/` へフォルダごとコピーすれば `$devday-judge-evidence` 等として選択できます。[公式の探索場所と呼び出し方法](https://learn.chatgpt.com/docs/build-skills)を参照してください。このPoCの作成ではユーザー設定や提出リポジトリへのインストールは行っていません。

```text
$devday-judge-evidence で /absolute/path/to/submission を一次審査してください。
```

各フォルダには `SKILL.md`、UI用の `agents/openai.yaml`、`references/` 内の採点基準・発表照合表・出力仕様が入っています。共通の3参照ファイルは意図的に各Skillに同梱しています。1フォルダだけ移動しても参照が切れず、他の2つの導入は不要です。基準を変える場合は、比較可能性を保つため3フォルダの参照版を揃えて更新します。

## 3方式を比較する場合

同じ提出物の同じ状態を、別々の新規セッションで評価してください。各セッションには使うSkillを1つだけ指定し、他方式の点数や講評を渡しません。対象範囲、補足資料、モデル設定、利用ツール、審査に使える資源を揃えます。作業ツリーが変わった場合は比較結果に明記します。

点数差だけでなく、根拠の正確さ、取りこぼし、未確認の扱い、テーマの対応を見比べます。方式間の平均点・多数決・通過ルールはこのPoCでは定義しません。

プロンプトとしての振る舞いを確認するためのケースは [VALIDATION.md](VALIDATION.md) にあります。これらは実際の提出物で行う試行審査の受け入れ条件であり、採点精度を実証したベンチマークではありません。

## v1.1の評価方針と検証

テーマ点は発表との関連と活用の深さを評価します。モックや制作過程の利用だけを理由とする一律の点数上限は設けません。実装状態・証拠の確かさ・大会条件の充足状況を別に報告します。画像のない作品は、確認できる操作設計からUXを採点し、未観察の視覚品質を加減点しません。

JSON出力はschema_version / rubric_version = 1.1です。旧版とはテーマ点の意味が変わるため、v1.0との得点比較・混合集計は避けてください。全作品に同じ版と大会条件を適用します。

```sh
# 検証環境にPython 3とjsonschemaが必要です。
python3 skills/devday-judge-evidence/scripts/validate_report.py /tmp/report.json
python3 scripts/check_consistency.py
python3 -m unittest discover -s tests -v
```

試行審査の手順と記録形式は[calibration/PROTOCOL.md](calibration/PROTOCOL.md)にあります。機械検証の成功と、人間との比較による採点品質の検証は別に扱います。
