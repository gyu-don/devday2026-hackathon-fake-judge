## 提供制約の読み方

この記事はすべての項目が誰にでも同じ条件で使えるとは述べていない。例えばDecisions APIはlimited preview、Private Inferenceは今後のpreview、GPT-6.1 SolのUltrafastはcoming soonとして記載されている。地域・プラン・管理者設定の条件がある発表も含まれる。

利用可能性や参加者のアクセス権を推測しない。APIの存在・接続仕様がこの表で確定するわけでもない。接続を検証できない場合は`implemented_unverified`等で示し、未知のメソッド名だけを根拠に架空APIと断定しない。モックを実接続として加点することも避ける。

## 対応の分類

候補ごとにID、成果物のどこに対応するか、証拠ID、関係の種類、実装状態を記す。

- 関係の種類: `core`（主価値）、`supporting`（意味のある補助）、`development_only`（制作過程のみ）、`inspiration`（着想・体験の応用）、`mention_only`（名称の記載のみ）。
- 実装状態: `connected`（到達するコード上に接続がある。実動作の確認を意味しない）、`implemented_unverified`（接続を確証できないが該当処理がある）、`mock`（代替データ・処理）、`planned`（計画のみ）、`not_applicable`（利用記録や名称等で接続分類が適用されない）。

単なるOpenAI API利用は特定発表への適合を証明しない。通常のMCP、チャットUI、一般的なエージェントというだけではDD15、DD12、DD10に自動対応させない。Codexで作ったという主張だけを強い適合にしない。逆にREADMEに発表名がなくても、対応する仕組みと価値が確認できれば拾う。

## 適合度 0–10（40点とは別枠）

| 点数 | 判定 | アンカー |
| --- | --- | --- |
| 0 | mismatch | 読み取れた対象に、特定の発表との対応を示す証拠がない |
| 1–2 | mismatch | 名称、一般的なOpenAI利用、漠然とした着想だけに留まる |
| 3–4 | weak | 特定の発表への対応は説明できるが、制作過程のみ・計画中心・価値との接続が薄い |
| 5–6 | partial | 特定の新しい能力や体験が成果物に具体化し、利用価値との対応を説明できる。モックや未検証の重要部分が残る |
| 7–8 | strong | 新しい能力・体験が主要な利用価値または意味のある改善を支え、具体的な成果物の証拠がある |
| 9–10 | strong | 発表の可能性を深く捉え、重要な価値へ特に説得力をもって転換している |
| null | undetermined | 読取失敗などで対応を判断するための証拠にアクセスできない |

最も強く支持される関連を軸に全体を判断する。対応項目数は加点しない。実API利用を全発表に一律要求しないが、価値の中心がモック・計画だけならその限界を反映する。モック等によって発表固有の主要能力が未検証なままの作品は5–6を超えない。開発時の利用だけなら3–4を超えない。加入プラン・利用枠の大きさ自体は点数にならない。

「その発表の能力を外す／以前からの一般的な方法に替えると、何が変わるか」を確かめる。唯一無二の必須性までは求めないが、便利さ、品質、速度、共同作業等への具体的な寄与が必要。実測していない速度・コスト削減を数値で創作しない。

強い対応が1つあれば、弱い対応も列挙されていることだけで減点しない。テーマ適合が強くても4観点の品質は別評価。`mismatch`も作品自体の無価値や自動失格を意味しない。参加資格として実利用等が必要かは主催者の明示したルールに従い、ここで新たな参加条件を作らない。
