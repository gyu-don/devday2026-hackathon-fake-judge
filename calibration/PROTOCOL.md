# 試行審査と校正

目的は根拠の正確さ、繰り返しの安定性、人間の評価との乖離を確認すること。機械検証の成功を採点品質の実証としない。

## 提出ケース

`fixtures/`の5件は架空の最小提出物。実作品の代理ベンチマークではなく、テーマの境界を確かめるスモークテスト用。各ディレクトリだけを対象にし、この手順・期待値・他の採点結果を審査セッションへ渡さない。

- `generic-bot`: 一般的な定期処理。Dots等の製品利用に自動対応させない。
- `named-mock`: 名称だけのDecisions API。固定値を実接続としない。
- `event-design`: 発表に即したイベント自動化の設計とモック。関連性と未実装を別々に評価する。
- `cli-workflow`: 新CLI体験の制作記録。development_onlyを理由に一律4点上限としない。記録は提出者の主張であり独立検証済みとしない。
- `plain-cli`: GUIのない成果物。操作の説明をUXとして評価する。

## 実施

1. 主催者は使用許可のある実作品5〜10件を追加し、対象のコピーまたはcommitと内容ハッシュを固定する。大会条件、補足資料、モデル、設定、ツール、時間・トークン上限を全試行で揃える。
2. 人間の審査員が先に全4観点・テーマ・根拠・許容点数範囲を記録する。意見が割れた作品も残し、単一の正解点に無理に揃えない。
3. 各作品を各skillで3回、独立した新規セッションから評価する。他方式の結果や人間の採点は渡さない。JSON結果を対象外へ保存する。
4. 各結果に同梱のvalidate_report.pyを適用し、さらに人間が引用先と判断の対応を確認する。
5. READMEの説明量だけを変えた版、同じ画面の画像を添えた版も比較する。説明が新しい実質的証拠を追加していないかを確認してから差を解釈する。
6. 同一方式の観点別最大差、平均絶対差、人間の許容範囲からの逸脱、誤引用・重要な見落とし、方式ごとの平均的な高低、所要時間を記録する。主観的品質と機械契約の失敗を分ける。

同一作品・同一方式で3点以上の差、根拠の捏造、実接続とモックの混同があれば再調査する（暫定の調査基準であり合否閾値ではない）。3方式すべてに共通する誤りは共有基準を、特定方式だけなら証拠収集の手順を修正する。修正に使っていない作品でも再確認する。

大会条件のテストは同じ作品に「条件なし」「実利用必須」を指定して比較する。条件の充足判定は変わり得るが、条件だけを理由に品質点・テーマ点を変更しない。

## 記録形式

各試行に次を残す。実作品のコードや機密資料をこのリポジトリに保存する必要はない。

```json
{
  "case_id": "event-design",
  "snapshot": "内容ハッシュまたは固定commit",
  "skill": "devday-judge-evidence",
  "rubric_version": "1.1",
  "model": "実際のモデル名",
  "settings": "推論設定・ツール・予算",
  "event_rules": [],
  "run": 1,
  "report_path": "対象外に保存したJSON",
  "human_reference_path": "事前の人間評価",
  "contract_valid": null,
  "citation_errors": [],
  "missed_evidence": [],
  "elapsed_seconds": null
}
```
