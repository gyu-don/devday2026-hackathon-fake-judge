# 試行審査と校正 v2.0

目的は、根拠の正確さ、方式内の安定性、人間との整合性を保ちながら、3方式が異なる探索を実行できるかを確認すること。点数の意図的な分散は成功条件にしない。小規模fixtureの結果や機械検証だけで実作品の審査品質改善を断定しない。

## 変更前の設計で重複していたもの

基準となる旧実装のcommitは`ca78eb966dc2bd5d2354b8802dace87a36941419`。これは調査手順の参照用で、旧スコアを新スコアと直接比較するためではない。

| 箇所 | 旧指示の重複と影響 | v2.0での配置 |
| --- | --- | --- |
| Evidenceの手順3 | 少なくとも主機能1つの入力から結果までの追跡と、高評価の各主張に対する対立仮説が必須。Journey・Challengeの主手法も実行していた | 横断的な裏付け照合を主とし、経路・別説明はカバレッジ不足や矛盾時の局所補助へ |
| Journeyの手順4 | 別主機能・構成・テスト・導入・アクセシビリティ・採用・独自性と補完範囲が広く、網羅調査に近づく | 主シナリオの代表性を崩す重要な価値がある場合に追加確認 |
| Challengeの手順1と全領域確認 | 主張の選別前に入口から主要出力の経路確認が必須。全領域の問いも網羅調査へ広がりやすい | 各観点の採点を左右する主張を先に選び、判別する場所へ集中 |
| 共通rubric | 完成度・状態・回復・採用・洞察を細かく列挙し、短い説明でも実装から価値を探す等の探索指示が各方式に追加されていた | 採点上の意味・証拠の正確性は維持。探索の開始点、優先順位、広さ・深さ、追加条件、採点前確認は各Skillへ |
| 共通devday参照 | 全方式に同じ置換の問い・対応の追加確認を要求し、独立したテーマ点を再調査する構造だった | 能力を外した場合の差は評価対象・出力事実として共有。どの資料からどう確認するかは各方式で選ぶ |

共通rubricが単独で全方式に全く同一の順序を強制していたわけではない。各Skillの重複した必須手順と組み合わさり、似た調査に収束しやすいという静的な設計分析である。既存の近い点数の原因を実証した分析ではない。

公式4観点、等配点、詳細アンカー、0とnull、安全境界、証拠の正確性、基本出力は共通に保つ。方式固有なのは出発点、優先順位、探索範囲、追加調査・停止条件、採点前確認と観察構造。同じ重要な事実に到達することも、補助的に他方式に典型的な手法を使うことも許される。意図的に証拠を無視したり、採点を甘く・厳しくしたりしない。

## 提出ケース

`fixtures/`の6件は架空の最小提出物。各ディレクトリだけを審査し、この手順・期待値・他の採点結果を審査セッションに渡さない。提出コードは実行しない。

- generic-bot: 一般的な定期処理をDots等の固有能力に自動対応させない。
- named-mock: 名称だけのDecisions API。固定値を実接続としない。
- event-design: 発表固有の連携設計とモック。関連性と実現効果を分ける。
- cli-workflow: 新CLIの制作記録。通常のCodex使用と発表固有の寄与を区別し、自己申告を独立検証済みにしない。
- plain-cli: GUIなしでも用途に合う使いやすさを評価する。
- multi-path: CLIと別のローカルイベント入口がある。資料別の裏付け、通常・空入力・再配送の経路、固定テンプレートという別説明を区別できるケース。権限フィルターはあるが取得は未実装、重複排除はメモリのみ。どの方式にも同じ事実を読む権利があり、意図的な見落としを期待しない。

実作品5〜10件も使用許可を得て追加する。多数機能の一部に価値が偏る作品、主経路以外に重要な設計がある作品、説明と実装が異なる作品等を含める。fixtureの固定正解点は設けない。

## 条件AとBの用意

旧版と新版の点数は審査観点が違うため直接比較しない。両条件とも公式4観点・schema_version / rubric_version=2.0で比較する。

- 条件A: 公式4観点へ移行し、従来の探索順序と補完の広さをほぼ維持。旧版の「主機能の経路＋対立仮説」を要求するEvidence、広い補完を要求するJourney、最初に主要経路を読むChallengeを残す。
- 条件B: このリポジトリのv2.0 Skill。探索手順を分離する。

`python3 scripts/prepare_condition_a.py /tmp/devday-condition-a-UNIQUE`で、実験用のAを空の新規ディレクトリへ作る。同梱の`condition-a/`は旧手順の要点をv2.0の観点名・出力に移植した実験用手順で、旧版そのものの再現ではない。採点を持たない実装証拠の調査は維持する。Bの共通4参照・バリデーター・UI metadataをそのままコピーし、SKILLの調査方法部分だけを置き換える。通常の配布Skillには影響しない。準備スクリプトとfixtureはジャッジの実装・校正用で、提出物内では実行しない。

実験前に人間がAの旧手順との対応とA/B差分を確認する。共通ファイルのSHA256、3つのSKILLのSHA256、固定作品の内容ハッシュ、使用プロンプトを保存する。A/Bで採点アンカー・出力契約・参照資料が同一であり、差が探索手順に限定されることを確認する。旧版の出力ラベルを新キーへ機械的に置換した得点は比較データにしない。

## 実施

1. 主催者は対象のコピー・commitと未追跡ファイルを含む内容ハッシュを固定し、開始・終了時に検証する。両条件・全方式で同じ作品、補足資料、モデルの実版、推論設定、ツール、時間・トークン予算を使う。参加資格は遵守済みで入力に条件差を設けない。
2. 人間が先に4観点の評価と許容範囲、重要な事実、根拠、想定される見落としを記録する。意見が割れた作品も残す。
3. 各条件×各方式×各作品を3回以上、独立した新規セッションで評価する。順序は無作為化または釣り合わせる。1セッションに1方式だけを渡し、他の結果・期待値・人間評価は渡さない。結果は提出物外へ保存する。
4. 同梱validate_report.pyで検証する。続いて人間が引用先と観察の対応、モック境界、未確認と不存在、各得点帯の根拠を監査する。形式違反と判断の誤りを分ける。
5. 同じコードで説明量だけを変えたペア、画像有無のペアも比較する。追加資料が新しい実質的証拠を加えたか確認して差を解釈する。
6. 下記7項目をA内、B内、A/B間で比較する。手順を修正した場合は別の実験版として固定し、修正に使っていない作品でも確認する。

## 比較する7項目

| 項目 | 記録・解釈 |
| --- | --- |
| 観点別スコアの一致・不一致 | 各点、差、平均絶対差、得点帯の移動、null率を記録。nullは0へ変換せず、有効な比較数を併記。同点でも不一致でも根拠を点検する |
| 参照した証拠の重複率 | ファイル、シンボル/行、観察した事実、影響した観点の各レベルを区別。集合のJaccard=積集合/和集合、空和集合はnull。IDは各レポート内のラベルなので比較キーにしない |
| 各方式だけが見つけた重要な事実 | 人間が意味の同じ観察を統合し、他方式に本当にないか、どの観点のどの判断を変えるかを確認。表現差だけの独自性を数えない |
| 根拠の正確性 | 引用先、シンボル、読めた内容と観察の対応、直接観察/主張/推定を点検する |
| 誤引用・重要な見落とし | 誤引用の件数と重要度、事前の重要事実の検出状況、実接続とモックの混同、実行の捏造を記録する |
| 同一方式内の安定性 | 反復の観点別レンジ・平均絶対差、同じ重要事実の検出率、nullと確信度の変動を記録する |
| 人間との整合性 | 人間の許容範囲からの距離、根拠の一致、許容される見解差を記録し、単一の正解点へ無理に揃えない |

`python3 scripts/compare_reports.py left.json right.json`は2つのv2.0レポートを検証し、点数差、引用証拠のパス・位置・観察文・影響観点の重複、独自の証拠候補、方式固有の観察をJSONで並べる。別ターゲットのメタデータや審査中の変更は拒否するが、同一内容は外部の固定ハッシュで確認する必要がある。意味の同じ別表現・異なる粒度の位置は自動統合しない。候補の重要性・根拠の真偽・独立性は判定しない。

同じ小規模リポジトリなら同じファイル・関数を読むのは自然。高い重複率だけで独立性不足としない。観察が同じでも、Evidenceのカバレッジ確認、Journeyの成果到達確認、Challengeの主張判別という異なる検証が実施されたかをmethod_observationsと許可された読取操作ログで確認する。内部の思考過程は収集しない。逆にファイルが違っても同じ説明を引用しただけなら独立性の証拠にならない。

## 結果の判断

同点の場合は、同じアンカーを支持する事実と、その事実に至った確認範囲・検証対象が独立に追認できれば妥当な収束と扱う。同じ一般説明の反復や空の観察だけなら形式的な一致の疑いとして再調査する。ログがなく区別できない場合は独立性を未確認と記す。

差がある場合は、発見事実、確認範囲、モック境界、未確認、得点帯の解釈へ差の原因を紐付ける。探索差でなくアンカーの不統一なら共通基準を直す。同一方式で3点以上の差、捏造、接続とモックの混同は再調査の暫定基準で、合否閾値ではない。

成功条件は、異なる探索戦略が実行され、重要な事実の補完が増える可能性が示され、同点・差の原因が追跡でき、正確性・再現性を損なわないこと。品質指標が悪化していれば、スコア差や低い証拠重複だけで成功としない。実作品・反復・人間評価の結果を含めて報告する。

## 記録形式

各試行に以下を残す。実作品のコードや機密資料をこのリポジトリに保存する必要はない。

```json
{
  "case_id": "multi-path",
  "snapshot": "未追跡を含む内容ハッシュ",
  "condition": "B",
  "skill": "devday-judge-evidence",
  "skill_sha256": "実際の値",
  "shared_contract_sha256": {},
  "schema_version": "2.0",
  "rubric_version": "2.0",
  "model": "実際のモデル実版",
  "settings": "推論設定・ツール・予算・プロンプトの版",
  "run": 1,
  "report_path": "対象外に保存したJSON",
  "read_log_path": "利用可能なら読取操作のログ、なければnull",
  "human_reference_path": "事前の人間評価",
  "contract_valid": null,
  "citation_errors": [],
  "missed_important_facts": [],
  "unique_important_facts": [],
  "elapsed_seconds": null

```

証拠比較の人間用台帳には、正規化した事実ID、path、symbol/locator、観察事実、重要度、影響観点と評価への影響、各条件・方式・反復での検出、引用の正確性を残す。

v2.0のSchema・整合性・参照ID・方式形式・比較補助・条件A準備は機械検証の対象。fixtureを使った独立モデルセッションの反復試行、および実作品・人間との比較は未実施。探索分離は指示設計として実装したが、審査品質や実際の独立性の改善はまだ実証していない。実際のコマンド結果はVALIDATION.mdに記録する。
